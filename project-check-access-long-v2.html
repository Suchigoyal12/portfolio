Section 01
System

Unpacking a distributed architecture.

Permissions in UiPath aren't stored in one place — they are the output of dynamic, distributed system logic. Because groups, roles, and nested folders interact across multiple services, a user's effective access is the output of distributed logic, not a static assignment.

ARCHITECTURE LOGIC

User Identity / AD Group
↓   cascades to
Layer 02
Assigned Role
↓   bound to
Layer 03
Scope (Tenant → 6-Level Folders)
Section 02
Problem

The cost of decentralised chaos.

"What access does this user actually have across the platform?

Because permissions were scattered across Orchestrator, Data Service, Automation Ops and multiple other services; admins had to manually cross-reference identity dashboards against nested folder policies. This inability to reliably trace the origin of access made routine audits exceptionally tedious and increased the risk of misconfiguration.

⏱  Time-Consuming
🔨  Error-Prone
🔍  Hard to Audit

Challenge

Visualizing effective access without exposing system complexity.

Indirect and inherited access

Section 04
Decisions

Four decisions, four trade-offs.

01

Progressive Access Disclosure

WhyAccess is computed across multiple layers. Showing everything at once obscures what matters. AltFlattening all access details (roles, permissions, origin) in a single expanded view. RejectedHigh noise, poor scanability. Trade-offRequires an extra drill-down click for micro-level inspection.
02

Explicit Scope Separation

WhyAdmins required immediate distinction between globally scoped roles and localized roles. Trade-offIntroduces segmented views instead of a perfectly unified list. Some wouldn't call it a tradeoff!
03

Origin Traceability

WhySeeing that a user has access is useless if the admin cannot trace the identity rule that granted it. AltDisplay roles without inheritance or origin details. RejectedForced admins to manually trace access across systems, breaking audit workflows. Trade-offIncreased data density in the grid, requiring tighter layout and column prioritization.
04

Prioritizing Traceability over Actionability

WhyAdmins first need to understand why access exists before modifying it. AltAllow direct editing of roles within the audit view. RejectedIntroduced complexity and risk of incorrect changes without full context. Trade-offRequires navigation to source systems for action, but ensures safer decision-making.

V1 — INITIAL SOLUTION (PRIVATE PREVIEW)

Consolidating access visibility across services.

The MVP version focused on bringing fragmented access data into a single, navigable interface. It reduced the need for administrators to scrutinise multiple systems to understand user permissions.

Satiswar Dash (Senior Designer) led V1. I worked on it, under his mentorship — and led the work from V1.5 onward.

Entry Point

Introduced Check Access within Manage Access.

Positioned as an audit tool for user access.

Role Assignments

Consolidated roles across services.

Organized via left navigation hierarchy.

Permissions

Enabled deeper inspection when needed.

WHERE V1 STOPPED SHORT
V1 proved the concept. Four limits were visible before any feedback came in — and they set the scope of what I led next.
  • · Unclear assignment visibility
  • · Ambiguous navigation behaviour across levels
  • · Limited visibility into absence of access
  • · Entry point ambiguity against Manage Access

Three questions admins kept asking.

Through UiPath Private Preview and UiPath Insider Program research, we identified key gaps in how administrators understood and navigated access.

"
What kind of role is this and where does it apply?
Access structure lacked clarity

System didn't differentiate tenant / service / folder roles.

"
Where is this permission actually coming from?
Permission origin was unclear

Admins couldn't trace access from groups or folders.

"
Okay.. I see the access. Do I navigate back to the service to fix it?
Actionability was missing

Users could view, but not easily act on insights.

Key Takeaway

These gaps became more evident when the feature was used in real-world scenarios. Actionability and traceability were the missing links that prevented this from being a complete workflow.

V1.5 — DESIGNING UNDER CONSTRAINT

The ideal vs. the shipped.

The Engineering Constraint
The Design Decision
APIs couldn't support deep hierarchy without performance trade-offs. Full traceability wasn't feasible.
I focused on improving clarity and structure of access data, making it interpretable without full traceability.
User Insight

Research showed that administrators primarily needed to quickly understand what access exists and where it applies, before tracing its origin.

Outcome · Reduced ambiguity.

Outcome · Faster comprehension.

Section 08
V2 — Final
V2 — VISIBILITY TO TRACEABILITY

Centralized, explicit, and traceable.

Admins no longer just audited access — they could explicitly map it. The UI now fully matched their mental model of investigating.

Who → What Role → What Scope → Why.

Option ADropdown-Based Selection

Allowed users to select folder paths via a dropdown.

Limitation · Lacked visibility into hierarchy and made it difficult to understand structure at a glance.

Option B · SelectedTree Navigation

Introduced a persistent folder tree.

Enables users to explore hierarchy and understand context while auditing access.

Why Tree Navigation
  • Handles deep, multi-level structures
  • Provides spatial understanding of hierarchy
  • Reduces cognitive load compared to recalling paths
  • Enables faster debugging of access issues

Section 11
Learnings

Designing for complex data structures.

The structure is the experience.

01

The hardest problem wasn't UI — it was modeling access in a way admins could understand. I designed around user mental models (who has access where) instead of backend structures (roles, inheritance chains).

Complexity requires narrative.

02

When presenting dense data, you can't just show everything at once. Progressive disclosure is a form of storytelling — guiding the user through layers of complexity only when they ask for it.

Edge cases are the system.

03

In access management, the "happy path" is rarely the reality. We had to account for inherited access, conflicting permissions, and deeply nested folder structures from day one of designing the interactions.

Clarity over completeness.

04

When full hierarchy traceability wasn't technically feasible, I prioritized making existing data interpretable rather than introducing partial or misleading representations.
